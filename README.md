## 1. Назначение и роль

Панель - это веб-клиент для нагрузочного стенда. Она показывает живую телеметрию (состояние, силу сжатия, угол вала, диагностику) и позволяет
управлять стендом кнопками. Панель предназначена оператору на ноутбуке или сервере в той же локальной сети, что и стенд.

Разделение ролей: **стенд - это сервер** (он хостит REST и WebSocket), **панель - клиент**. Панель ничего не размещает на устройстве и живёт
отдельно, статикой на любом хосте. Устройство наружу само ничего не шлёт.

Панель - тонкий клиент: она не хранит состояние на сервере, не имеет собственного бэкенда и полностью восстанавливает картину из потока телеметрии.
При недоступном стенде она показывает отсутствие данных и переподключается, а не падает.

## 2. Стек и обоснование

| Что | Выбор | Почему |
|---|---|---|
| Сборщик | Vite | быстрый dev-сервер, простая статическая сборка |
| Фреймворк | React 18 + TypeScript | строгая типизация протокола, компонентная модель |
| График | uPlot | лёгкая и быстрая библиотека на потоковых данных |
| Шрифт | Inter Variable | self-hosted, с кириллицей, упакован в сборку - работает офлайн, без обращения к CDN |

Ключевые свойства сборки:

- **Выход - статический `dist/` + маленький сервер координации** (`server/`, Node без зависимостей): раздаёт статику, ведёт канал управления и журнал (раздел 11).
- **Относительные пути ассетов** (`base: "./"`). Панель работает и из корня домена, и из под-пути.
- **Единственные зависимости времени выполнения** помимо React - `uplot` и шрифт. Никаких тяжёлых UI-библиотек.
- **Офлайн-совместимость.** Шрифт и все ассеты локальны, панель не зависит от внешних сервисов.

Интерфейс на русском языке, тёмная тема по умолчанию.

## 3. Адрес стенда: резолвинг хоста

IP стенда **не зашивается** в сборку. Он резолвится в рантайме (`src/config.ts`) по строгому приоритету:

1. `localStorage["press.stand_host"]` - задаётся полем в шапке, действует для конкретного браузера;
2. `import.meta.env.VITE_STAND_HOST` - необязательный дефолт этапа сборки (из `.env`);
3. встроенный дефолт.

Обоснование такого подхода:

- **Один и тот же бандл работает с любым стендом.** Адрес меняется в шапке без пересборки, что важно при DHCP или нескольких стендах.
- **Адрес всегда виден и сбрасываем.** Поле ввода в шапке показывает текущий хост; кнопка сброса очищает сохранённое значение и возвращает дефолт. Это сделано сознательно: сохранённый в `localStorage` адрес не должен «залипать» незаметно.
- **Доступ к `localStorage` защищён** обработкой исключений, поэтому приватный режим браузера или открытие из файла не ломают резолвинг - он просто падает в дефолт.

mDNS-имя (`.local`) намеренно не используется: оно не резолвится на части точек доступа. Работа идёт по IP; при появлении назначаемого домена
его достаточно вписать в поле хоста или в `.env`.

Панель строит из хоста два адреса: HTTP-базу (`http://<host>`) для REST и WebSocket-URL (`ws://<host>/ws`) для потока телеметрии.

## 4. Архитектура данных

Поток данных однонаправленный и простой:

```
useStand(host)  ──владеет──▶  WebSocket-соединение со стендом
      │
      ├─ telemetry   последний кадр телеметрии
      ├─ history     буфер точек для графика
      ├─ log         журнал событий и команд
      ├─ status      состояние соединения
      └─ send / sendConfig   отправка команд и конфигурации
      │
      ▼
    App  ──props──▶  презентационные компоненты (карточки)
```

- **`App`** держит только два элемента состояния: текущий хост и флаг «есть неприменённые правки диапазона» (`configDirty`). Всё остальное - в хуке.
- **`useStand(host)`** - единственный владелец соединения и всех живых данных. Компоненты получают данные через props и сами ничего не запрашивают.
- **Компоненты** презентационные: рисуют то, что пришло, и вызывают колбэки на действия оператора.

Такое разделение держит всю сетевую сложность в одном месте и делает компоненты предсказуемыми и легко заменяемыми.

## 5. Хук useStand: соединение и данные

`src/hooks/useStand.ts` - ядро панели. Он владеет WebSocket-соединением, переподключением, разбором сообщений, отправкой команд, буфером графика
и журналом. Возвращает объект: `status`, `telemetry`, `history`, `log`, `send()`, `sendConfig()`, `reconnect()`.

### Соединение и переподключение

- При открытии соединения хук помечает попытку номером и пишет живую строку в журнал.
- **Свой таймаут попытки** (около 6 секунд): если сокет не открылся за это время, попытка принудительно закрывается и планируется следующая. Это нужно, чтобы не висеть на долгом TCP-таймауте браузера (десятки секунд).
- **Экспоненциальный backoff**: задержка между попытками растёт с множителем, до потолка (около 15 секунд). При успешном подключении задержка сбрасывается к минимуму.
- При смене хоста соединение пересоздаётся с чистого листа, счётчик попыток и задержка сбрасываются.
- Перед новой попыткой со старого сокета снимаются все обработчики и он закрывается, чтобы асинхронное закрытие старого соединения не запустило лишнее переподключение.

### Журнал соединения

Строки подключения показываются единообразно, без бегущих таймеров: «Попытка N: подключение…» → «Попытка N не удалась. Следующая в ЧЧ:ММ:СС» →
«Подключено». Реализовано через «живую» строку, которая обновляется на месте, а при завершении попытки «отстёгивается» как постоянная запись.
Это не засоряет журнал тикающими отсчётами.

### Разбор входящих сообщений

Каждое сообщение разбирается в порядке: сначала проверяется, событие ли это (`event`), иначе - телеметрия. Порядок важен: телеметрия не содержит
поля `event`.

- **Телеметрия** сохраняется как последний кадр и добавляет точку в буфер графика (время по часам клиента, значение силы).
- **Событие** превращается в строку журнала:
  - `ack` разбирается на команду и результат: `ok` → «команда принята», `ignored_<состояние>` → «команда отклонена (человекочитаемое имя состояния)»;
  - `tare` при успехе разбирается на новый и прежний ноль, показывается величина убранного дрейфа в граммах (перевод через известный коэффициент калибровки);
  - `state`, `park`, `error`, `wall` пишутся как события своего типа с цветовой пометкой.

### Отправка команд

`send(cmd)` работает по WebSocket текстовым фреймом (просто слово `seek`/`home`/`stop`/`tare`). Если сокет закрыт, идёт **резервный путь через REST**:
`POST /v1/command?cmd=...` с разбором кода ответа. Таким образом команда доходит даже при временно закрытом WebSocket.

Запись конфигурации `sendConfig(target, min, max)` всегда идёт через REST: `POST /v1/config?target=&min=&max=`. Ответ прошивки (принято или отклонено
с причиной) - определяющий, панель показывает его в журнале.

### Буферы

- **История графика** ограничена (около 600 точек, примерно 2 минуты при 5 Гц). Старые точки отбрасываются, буфер живёт в памяти вкладки и обнуляется при перезагрузке.
- **Журнал** ограничен по числу строк, старые записи вытесняются.

## 6. Протокол: типы телеметрии, событий, команд

Формы данных описаны в `src/types.ts` и точно повторяют то, что шлёт прошивка. Это контракт между панелью и стендом - имена и типы менять нельзя
без согласования с прошивкой.

### Телеметрия

Кадр телеметрии приходит по WebSocket примерно 5 раз в секунду. Поля: состояние автомата, сила (`load_kg`), целевая нагрузка и границы окна,
сырой отсчёт, готовность датчика, аптайм, абсолютный и относительный угол энкодера, флаг аварии.

Два поля опциональны: `load_offset` (текущий ноль тензодатчика) и `tare_ok` (готовность к перетарированию). Они помечены необязательными, чтобы
панель проходила проверку типов и со старой прошивкой, где этих полей ещё нет.

### События

Событие несёт тип (`state` / `park` / `error` / `wall` / `ack` / `tare`), строковую детализацию и аптайм. Формат детализации зависит от типа:
для `ack` - `<команда>:ok` или `<команда>:ignored_<состояние или причина>`; для `tare` - `off=<новый> prev=<старый>`.

### Команды

Команда - это одно из слов: `seek`, `home`, `stop`, `tare` (команды калибровки идут отдельно через `POST /v1/calib` с токеном входа). Панель отправляет их как текстовый фрейм по WebSocket (или через REST в резерве).

### Единицы измерения

Панель работает только с силой (`load_kg`) и целевой нагрузкой. Полей тока, напряжения и мощности нет и не ожидается - это механический стенд.
Единицы отображения адаптивные: значения меньше 1 кг показываются в граммах, от 1 кг - в килограммах; при отсутствии данных показывается
прочерк без единицы. Это чисто отображение (`src/format.ts`), на стороне API ничего менять не нужно. Порог переключения берётся по модулю,
поэтому небольшой отрицательный шум около нуля читается в граммах, а не переключает единицу.

## 7. Логика доступности кнопок

`src/standLogic.ts` вычисляет, доступна ли кнопка в текущем состоянии, какую команду она пошлёт и почему заблокирована. Эта логика
**зеркалит переходы прошивки**: панель не должна предлагать действие, которое устройство отклонит. Итоговое решение всегда за прошивкой,
но панель заранее гасит заведомо недоступные кнопки и объясняет причину.

На каждую кнопку функция возвращает: доступность, команду, надпись на кнопке (реальный токен состояния прошивки), русское пояснение
и причину блокировки.

### Кнопка поиска (SEEK)

| Состояние | Доступна | Действие |
|---|---|---|
| `IDLE` | да | `seek` - начать поиск |
| `HOLD_LOAD` | да | `seek` - повторный поиск к новой цели |
| `SEEK_LOAD` | нет | поиск уже идёт |
| `HOMING` / `RETURN_HOME` | нет | идёт движение |
| `ERROR` | нет | сначала восстановление |
| нет связи | нет | нет данных о состоянии |

### Кнопка возврата/homing (HOME)

| Состояние | Доступна | Действие |
|---|---|---|
| `SEEK_LOAD` / `HOLD_LOAD` | да | возврат домой |
| `IDLE` | да | homing по требованию (идемпотентный) |
| `ERROR` | да | восстановление из аварии |
| `HOMING` / `RETURN_HOME` | нет | homing уже идёт |
| нет связи | нет | нет данных о состоянии |

### Кнопка перетарирования (RE-TARE)

Доступность этой кнопки считается не по состоянию, а по **полной телеметрии**. Если прошивка присылает поле `tare_ok`, кнопка следует
его вердикту напрямую; причина блокировки при этом выводится из той же телеметрии (не в `IDLE`, датчик не готов, вал не в нуле, есть нагрузка)
чтобы не дублировать пороги прошивки. Если поля `tare_ok` нет (старая прошивка), панель откатывается к простому правилу «доступно только в IDLE».

### Калибровка нуля кулачков (CALIBRATE)

Кнопка `CALIBRATE` доступна в `IDLE` и `ERROR` и только если прошивка присылает поле `home_abs_deg` (признак поддержки калибровки).
Нажатие открывает окно входа: логин и пароль проверяет прошивка (`POST /v1/calib`), панель их не хранит. После входа стенд переходит
в `CALIBRATE`, кулачки **стоят**.

Пока стенд в `CALIBRATE`, над карточкой управления видна панель калибровки (`CalibrationCard`):

- **плавное вращение** «−» / «+» до кнопки «Стоп»;
- **поворот на угол** 1 / 5 / 10° в выбранную сторону (шаг мотора 0,45°, поэтому 1° ≈ 0,9°);
- **«Сохранить как ноль»** (с подтверждением вторым нажатием) и **«Отмена»** (ноль не меняется, вал едет к прежнему нулю).

Управлять может только тот, кто вошёл в этой вкладке и владеет каналом управления. Токен входа живёт только в памяти вкладки (`useCalib`):
после выхода из режима калибровки или перезагрузки страницы нужен повторный вход. Если стенд уже в `CALIBRATE` (например, после
перезагрузки), на панели есть кнопка «Войти». Красная `STOP` в карточке управления останавливает движение обычной командой `stop`.

### Блокировка повторного поиска из удержания

Есть отдельное правило на стороне панели: если в состоянии `HOLD_LOAD` есть **неприменённые правки диапазона** (флаг `configDirty`), кнопка поиска
блокируется с пояснением «сначала примените изменения диапазона». Иначе повторный поиск ушёл бы к старой, ещё не отправленной цели. Это забота
интерфейса, а не логики прошивки.

### Метаданные состояний

`stateMeta()` переводит токен состояния в русскую подпись и «интент» (тип оформления: ожидание, движение, homing, удержание, авария, загрузка).
Подпись используется в карточке статуса и в журнале; цвета привязаны к интенту в стилях.

## 8. Компоненты интерфейса

Все компоненты в `src/components/`. Они презентационные: получают данные через props и вызывают колбэки на действия.

| Компонент | Что делает |
|---|---|
| `Header` | поле ввода хоста (Подключить / Сброс), переключатель темы, индикатор соединения |
| `StatusCard` | текущее состояние крупно (по-русски, с цветовой лампой), готовность датчика, аптайм |
| `ForceCard` | сила сжатия крупно (адаптивные единицы), ниже - цель и сырой отсчёт |
| `AngleDial` | SVG-круг с точкой на относительном угле; логический ноль справа, диагностика абсолютного угла и флага аварии |
| `ControlsCard` | три кнопки: поиск, homing/возврат, перетарирование; надпись-токен, пояснение и причина недоступности |
| `TargetRangeCard` | задание целевой нагрузки и границ окна со степперами, кнопка «Применить» |
| `Stepper` | поле ввода числа с кнопками вверх/вниз |
| `ForceChart` | график силы во времени (uPlot), пунктир - целевая нагрузка |
| `EventLog` | журнал событий и команд с автоскроллом |

### Заметные решения

- **Круг угла (`AngleDial`).** Логический ноль вынесен вправо (положение 3 часа), как на реальном стенде, положительный угол идёт против часовой стрелки. Рядом - абсолютный угол энкодера и флаг аварии; при аварии точка текущего угла подсвечивается тревожным цветом.

- **Ввод чисел (`Stepper`).** Поле работает через текстовый черновик, а не «жёсткое» числовое поле. Это позволяет свободно набирать дробные значения и промежуточные состояния ввода. Наверх передаётся только валидное число; при потере фокуса черновик нормализуется. Внешнее значение не затирает набор, пока поле в фокусе.

- **Карточка цели и диапазона (`TargetRangeCard`).** Поля заполняются из первого кадра телеметрии, но только один раз и только пока оператор их не трогал - чтобы поток 5 Гц не затирал ввод. Клиентская валидация (цель в пределах диапазона, границы корректны) блокирует отправку заведомо неверных значений; окончательный вердикт выдаёт прошивка. При изменении полей поднимается флаг «неприменённые правки», который гасит повторный поиск из удержания (см. раздел 7). Карточка перемонтируется при смене хоста, чтобы перечитать значения нового стенда.

- **График (`ForceChart`).** Цвета читаются из CSS-переменных темы и график пересоздаётся при смене темы (canvas не видит CSS-переменные напрямую). Ширина подгоняется под контейнер.

- **Журнал (`EventLog`).** Автоскролл вниз работает только пока оператор находится у нижнего края; если он прокрутил вверх читать историю, новые записи не «утаскивают» его вниз.

## 9. Темы и оформление

Панель поддерживает тёмную (по умолчанию) и светлую темы, переключатель в шапке. Выбор сохраняется в `localStorage` и применяется через атрибут
`data-theme` на корневом элементе. Системная тема намеренно не отслеживается - для цехового ПК важнее предсказуемость, а не автоподстройка.

Все цвета заданы в цветовом пространстве oklch, сетка кратна 4 пикселям. Тёмная тема построена на нейтральном charcoal с синим акцентом, светлая
на нейтральной серой палитре. Хук `useTheme` хранит выбор и переключает темы.

## 10. Соответствие прошивке

Панель жёстко связана с контрактом прошивки в нескольких местах - при изменении прошивки эти места нужно держать в синхроне:

- **`src/types.ts`** повторяет структуру телеметрии и событий один в один. Имена и типы полей менять нельзя без согласования - это ровно то, что шлёт устройство.
- **`src/standLogic.ts`** зеркалит матрицу переходов прошивки. Если в прошивке меняется, из каких состояний доступна команда, это правило нужно обновить и здесь.
- **Команды** - текстовые фреймы `seek`/`home`/`stop`/`tare`; резервный путь REST шлёт `POST /v1/command?cmd=`. Запись конфигурации - `POST /v1/config`.
- **Константы стенда** (целевая нагрузка, границы, домашний угол) захардкожены в `src/config.ts` как значения-заглушки до прихода первого кадра телеметрии. После подключения они перекрываются живыми значениями. Их источник - параметры прошивки.
- **Коэффициент калибровки** используется в панели только для перевода дрейфа при перетарировании в граммы для журнала. Его нужно держать синхронным с прошивкой.

## 11. Канал управления, журнал, сборка и деплой

Рядом с панелью работает небольшой сервер координации (`server/`, только стандартная
библиотека Node, без зависимостей). Он раздаёт собранную статику вместо nginx и добавляет
две вещи, которые нельзя сделать в одном браузере.

### Канал управления

Управлять стендом одновременно может только один человек, остальные смотрят телеметрию.

- **Занять.** Полоса «Канал управления» над карточками: ввести имя, нажать «Занять
  управление». Кнопки стенда и «Применить» разблокируются только у владельца. У остальных
  на кнопках замок и надпись «Канал занят: <имя>».
- **Освободить / передать.** Владелец может освободить канал или передать его любому, кто
  сейчас на связи (выпадающий список + «Передать»).
- **Попросить.** Зритель жмёт «Попросить управление». Владелец получает уведомление
  (всплывающее окно, звук, мигающий заголовок вкладки; системное уведомление - только
  при открытии по https/localhost) с кнопками «Передать» / «Отклонить». Если владелец за
  `LOCK_REQUEST_TIMEOUT_S` не ответил и **ничего не сделал**, канал переходит к
  запросившему автоматически. Если владелец за это время работал со стендом, запрос
  просто истекает.
- **Забыли освободить.** Без действий (команд, применения параметров, «Продлить») канал
  освобождается через `LOCK_IDLE_TIMEOUT_S`. За минуту до этого владелец получает
  предупреждение с кнопкой «Продлить». Освобождение канала **не останавливает стенд**:
  идущий прогон продолжается, просто управлять им теперь может другой.
- **Закрыли вкладку.** Канал держится `LOCK_DISCONNECT_GRACE_S` (перезагрузка страницы
  его не теряет), потом освобождается. Если кто-то уже просил управление, канал
  переходит к нему сразу.
- **Очередь.** При освобождении канал сразу отдаётся первому из тех, кто просил.
- **Нет связи с сервером координации** - просмотр работает, управление заблокировано
  (иначе двое снова смогут нажимать кнопки одновременно).

Канал ведётся отдельно для каждого адреса стенда из шапки (`192.168.3.53` и
`1.esp32-s3.local` - это разные каналы, поэтому всем лучше использовать один и тот
же адрес). Блокировка работает на уровне панели: прошивка про неё не знает, поэтому
запрос к стенду напрямую (curl, другая копия панели, физическая кнопка) она не
остановит. Такие команды, отправленные через панель без права, помечаются в журнале.

### Журнал

Сервер пишет на диск (`logs/<дата>/`):

- `journal.jsonl` - кто занял, передал или освободил канал; кто какую команду отправил и
  какие параметры применил (с ответом стенда); события стенда (`state`, `ack`, `error`
  и т. д., без дублей, даже если открыто несколько панелей); открытие/закрытие панелей и
  потеря/восстановление связи панели со стендом;
- `telemetry_<стенд>.jsonl` - телеметрия, прореженная до `LOG_TELEMETRY_INTERVAL_MS`.

Журнал пишется, пока открыта хотя бы одна панель этого стенда: данные со стенда
поступают через браузеры (сервер к стенду сам не подключается и не занимает слот WS).
Кнопка «Архив журналов» в карточке журнала: скачать по дням в CSV (для русского Excel:
разделитель `;`, десятичная запятая) или в исходном JSONL. Действия других людей также
появляются в экранном журнале у всех.

### Настройки (переменные окружения, `docker-compose.yml`)

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `LOCK_IDLE_TIMEOUT_S` | 600 | авто-освобождение канала при бездействии (0 - никогда) |
| `LOCK_DISCONNECT_GRACE_S` | 45 | сколько ждать владельца, закрывшего вкладку |
| `LOCK_REQUEST_TIMEOUT_S` | 60 | сколько ждать ответа на запрос управления |
| `LOG_TELEMETRY_INTERVAL_MS` | 1000 | шаг записи телеметрии (0 - не писать) |
| `LOG_RETENTION_DAYS` | 180 | сколько дней хранить журналы (0 - бессрочно) |
| `LOG_TZ` | пояс системы | часовой пояс времени в журналах |
| `LOG_DIR` | `./logs` | каталог журналов (в Docker - том `./logs`) |
| `PORT` | 80 | порт сервера |

### Запуск

```bash
npm install
npm run dev              # dev-сервер Vite, API координации встроен, журналы в ./logs
npm run build            # -> dist/
npm start                # боевой сервер: dist/ + API (PORT=80 по умолчанию)
docker compose up -d --build
```

Раньше `dist/` можно было положить на любой статический хост. Теперь панели нужен
`server/index.mjs` (или dev-сервер Vite): без API координации кнопки управления
заблокированы. `nginx.conf` больше не используется и удалён.

## 12. Масштабирование

Панель - тонкий клиент, поэтому «масштаб» здесь про раздачу статики и число одновременных вкладок.

- **Много клиентов сразу.** Ограничение не в раздаче статики (она тривиальна), а в самом стенде: лимит одновременных WebSocket-клиентов задан в прошивке (`NET_MAX_WS_CLIENTS`). Сверх лимита новое подключение закрывается. То есть живых панелей на один стенд - до этого числа.
- **Несколько стендов.** Один и тот же бандл работает с любым стендом, адрес задаётся в рантайме. Можно держать одну вкладку и менять адрес в шапке, либо разложить бандл под разные адреса.
- **Нагрузка данными.** Телеметрия идёт примерно 5 Гц. График хранит скользящее окно (около 2 минут) в памяти вкладки - история не растёт бесконечно, перезагрузка вкладки её обнуляет.
- **Кеширование.** Ассеты Vite содержат хеш в имени, поэтому их можно кешировать агрессивно; сам `index.html` - без долгого кеша.

## 13. Типовые проблемы

| Симптом | Причина и что делать |
|---|---|
| Вечное «Подключение… / Повтор подключения» | Стенд недоступен по WebSocket. Проверить `curl http://<ip>/v1/health`, затем вписать реальный IP стенда в поле хоста. |
| Панель открыта по `https://`, WebSocket не идёт | Браузер блокирует `ws://` из https-контекста (mixed content). Открывать панель по `http://`. |
| Правка дефолтного адреса в исходнике не применилась | В браузере залип сохранённый адрес. Нажать «Сброс» в шапке или очистить `localStorage`. |
| Соединение рвётся в браузере, но `curl` к `/ws` отвечает | Privacy-расширения или антифингерпринтинг браузера могут разрывать WebSocket. Проверить в чистом профиле, отключить блокировщики для адреса стенда. |
| Ассеты 404 после копирования в под-путь | Скопирована не вся папка `dist/`. Копировать целиком (`index.html` и `assets/`). |
| `esp32-s3.local` не резолвится | Ожидаемо: mDNS намеренно не используется. Работать по IP. |
